# WRITEUP: Evidence Chain of Custody (Lab 4.4)

This document maps the four chain-of-custody properties — **authenticity**,
**integrity**, **timeliness**, and **preservation** — to concrete artifacts
produced by the `grc-gate` pipeline, using a real pipeline run
(`run_id 31419052889`, PR #3) as the worked example.

## 1. Authenticity

**Claim:** The evidence bundle can be proven to have come from this
pipeline, signed at the time of that specific CI run, not forged or
substituted after the fact.

**Mechanism:** Cosign keyless signing (Sigstore/Fulcio/Rekor). The
`bundle-sign-upload.sh` script signs the evidence tarball with an
ephemeral key tied to the GitHub Actions OIDC identity, and the
signature is recorded in the public Rekor transparency log.

**Evidence:**
- Sigstore issued a short-lived certificate binding the signature to
  the workflow identity (`grc-gate.yml`, this repo, this PR).
- The signature was recorded in the Rekor transparency log at
  **index 2411325216**.
- `verify-evidence.sh` independently re-verifies this signature against
  Rekor on every check, rather than trusting a locally cached result.

## 2. Integrity

**Claim:** The evidence bundle stored in the vault is provably the exact
bytes produced by the CI run — any modification, however small, is
detectable.

**Mechanism:** SHA-256 checksum computed at signing time and stored
alongside the bundle (`*.sha256`), independently recomputed and compared
by `verify-evidence.sh` on every verification.

**Evidence — three real test states from this session:**

| State | Result |
|---|---|
| Original bundle, as uploaded by CI | `OK (fa76f239702c2eed41528b0b577d34ec9852304a2fafaff6957404d0b5cdfedc)` → `CHAIN INTACT` |
| Bundle overwritten in S3 with modified content | `FAIL: SHA mismatch` — verification halted immediately |
| Original version restored (via S3 `copy-object` from the untouched locked version) | `OK` → `CHAIN INTACT` again |

This demonstrates the check is a live, real comparison against the vault's
current object — not a rubber stamp.

## 3. Timeliness

**Claim:** The evidence can be tied to a specific point in time, not just
"signed at some point."

**Mechanism:** Three independent timestamp sources, cross-checkable
against each other:
- The GitHub Actions run timestamp (`run_id 31419052889`, PR #3).
- The Rekor transparency log entry timestamp (immutable, publicly
  auditable, tied to tlog index 2411325216).
- `receipt.json`'s `signed_at` field, generated by `make_receipt.py` at
  upload time and stored in the vault alongside the bundle.

Because these three timestamps come from independent systems (GitHub,
the public Sigstore infrastructure, and the pipeline's own receipt), an
attacker would need to compromise all three simultaneously to convincingly
backdate evidence.

## 4. Preservation

**Claim:** Once written, evidence cannot be deleted or silently replaced
for a defined retention window — and even an attempted overwrite doesn't
destroy the original.

**Mechanism:** S3 Object Lock in GOVERNANCE mode (configured in
`primitives/evidence-vault/`), combined with S3 versioning.

**Evidence:**
- `verify-evidence.sh`'s retention check confirmed the object was locked
  with `retain until 2026-08-11T18:37:51.385000+00:00`.
- During the tamper test, overwriting the object's key in S3 did **not**
  delete or replace the original signed version — Object Lock prevented
  that. Instead, S3 versioning created a *new* version, while the
  original (`VersionId 8XveljQ7h1cNLoyLcTcigktvtvNqItOL`) remained fully
  intact and retrievable underneath.
- Restoration was possible specifically *because* the original was
  preserved: `aws s3api copy-object` promoted the untouched original
  version back to "current," and its ETag
  (`78e043622dfb39472c79a262f977d7dd`) matched the pre-tamper original
  exactly, confirming byte-for-byte preservation.

## Summary

| Property | Mechanism | Verified by |
|---|---|---|
| Authenticity | Cosign keyless signing + Rekor tlog | `verify-evidence.sh` §2 |
| Integrity | SHA-256 checksum | `verify-evidence.sh` §1 |
| Timeliness | GH Actions + Rekor + receipt.json timestamps | Cross-referenced manually |
| Preservation | S3 Object Lock (GOVERNANCE) + versioning | `verify-evidence.sh` §3, tamper test |

The tamper test in particular demonstrates the chain is fail-closed: a
modified bundle is rejected immediately, and even a successful write to
the vault cannot erase the original evidence, only add a new (also
provable) version on top of it.
